## 2026-09-29: Spec v1.3, fulfillment pipeline becomes the primary product (Claude Code)
- **Decision:** re-center the spec on the primary user's workflow: piece-level allocation of open orders (order date, then net value per piece) → aggregate allocated lines into stops → k-means on lat/lon → per-cluster PyVRP loads on 53 ft trailers → compare iterations. The generic PyVRP feature tour moves to M6/M7 and lessons. Milestones are reordered (§15).
- **Reason:** the friend who is the real user answered a use-case questionnaire. He uses PyVRP after k-means to build truckloads, not to sequence stops; linear feet are the only load limit; one cluster can need several trucks; routes are open (no return to the depot); stops are at most 500 miles apart within a cluster and between consecutive stops; distance is haversine × 1.2 ("mileage cushion"), with no road routing; about 2,000 open orders per run; a result is better with fuller trucks, tighter clusters, and more revenue; his pain is manually interpreting the data. He confirmed piece-level (partial) allocation, and that allocated amount = net value per piece × allocated pieces.
- **Interpretations made in v1.3:**
  - Linear feet are stored as integer hundredths of a foot (53 ft = 5,300).
  - k-means runs on 3D unit vectors from lat/lon. Cluster diameter is enforced by bisecting over-limit clusters, not by PyVRP. Auto-k picks the smallest k whose clusters all pass the diameter check before repair.
  - Open routes: native if the pinned PyVRP supports it, otherwise zero-cost return edges, labeled. Legs over the limit are prohibited in the matrix. Both need M1 capability fixtures.
  - A stop larger than one trailer is split into several visits.
  - A fixed cost per truck steers PyVRP toward fewer, fuller trucks.
  - Metrics are shown side by side with non-dominated highlighting; there is no hidden composite score.
  - `MAX_STOPS` (500) now bounds each cluster solve; new `MAX_ORDERS` (5,000) and `RUN_WALL_LIMIT_SECONDS` (600).
- **Assumptions to confirm with him (non-blocking):**
  1. The 500-mile limits apply to haversine × 1.2, not raw haversine (it is a setting either way).
  2. The truck count is unlimited.
  3. The value tiebreak is per piece, not per order total.
  4. Multiple orders at one address combine into one stop.
  5. How he picks k today (his answer "K is coordinates" described the k-means features, not the cluster count).
  6. A scrubbed sample of orders and inventory, kept as a local fixture only and never committed (spec §14).

## 2026-09-30: Optimizer pins and PyVRP 0.14.0 capability findings (Claude Code)
- **Pins** (`services/optimizer/pyproject.toml`, locked in `uv.lock`): Python 3.13, pyvrp 0.14.0, ortools 9.15.6755, scikit-learn 1.9.1, numpy 2.5.3, h3 4.5.0, fastapi 0.142.2, pydantic 2.13.5, uvicorn 0.54.0; dev: pytest 9.1.1, httpx2 2.13.1, ruff 0.16.9. Latest stable on PyPI as of today. `httpx2` (pydantic's successor to httpx) replaces `httpx` for FastAPI's `TestClient` because Starlette deprecates `httpx` there; approved by the owner.
- **arm64:** every pin has cp313 `manylinux_2_28` wheels for both `x86_64` and `aarch64` (glibc ≥ 2.28; `node:24-slim` is fine). arm64 needs no source builds.
- **Open routes are a workaround, not native.** PyVRP 0.14.0 vehicle types always have an end depot and no open-route flag. Every stop → depot edge gets zero distance, so the return is free and excluded from reported distance. A fixture fails if a future pin adds an open-route parameter.
- **Prohibited legs are soft in PyVRP.** Missing edges are filled with `pyvrp.constants.MAX_VALUE` (2^44), a large finite cost. PyVRP avoids them whenever an alternative exists (e.g. an extra truck), but when a stop is only reachable by a prohibited leg it still routes it and reports the solution feasible. Fillrate's validator (`validate_loads`) re-checks every leg against the real matrix and marks the result infeasible (`leg_too_long`). The depot → first stop leg is subject to the limit too, so the pipeline should drop unreachable stops ("allocated, not loaded") before solving.
- **Units at the solver boundary:** distance in integer meters (500 mi = 804,672 m), linear feet in hundredths of a foot, fixed truck cost in the same units as distance (meters).
- **Unlimited trucks** are modeled as one available vehicle per stop.
- **API:** 0.14 separates locations from clients/depots (`add_location`, then `add_client(location, …)`); routes iterate `ScheduledActivity` objects; client activity `idx` is the 0-based client index.
- **Layout:** `services/optimizer/src/fillrate_optimizer/` (`travel`, `loads`, `capabilities`, `app`), tests in `services/optimizer/tests/`. FastAPI binds to 127.0.0.1 (`OPTIMIZER_PORT`, default 8000).

## 2026-09-30: M1 durable synthetic fulfillment slice (Claude Code)
- **Worker transport:** the internal routes are a separate Node HTTP server started from `instrumentation.ts`, bound to `127.0.0.1:${INTERNAL_PORT:-3100}` (`packages/db/src/transport.ts`), not Next.js routes. The public listener therefore never serves `/internal/*`. Each request must also come from a loopback socket address (never a forwarding header) and carry `Authorization: Bearer $WORKER_TOKEN` (timing-safe compare). Routes: `claim`, `heartbeat` (returns the cancel request), `events` (progress/terminal with atomic artifacts). Store errors map to 409 (stale lease, out-of-order/conflicting event, success after cancel), 413 and 400. Without `WORKER_TOKEN`, the web process writes a random `worker.token` (0600) next to the database for native development; the container entrypoint generates the env var instead. Build workers skip the listener (`NEXT_PHASE`).
- **Supervisor:** `fillrate-worker` (or `fillrate-optimizer` with `FILLRATE_WORKER=1`, as in the image) polls for claims and runs each pipeline in a `spawn` child process. A heartbeat that reports cancellation kills the child and then records `cancelled`; a 409 abandons the job; a child that dies without a result stops heartbeating so the lease expires and the job is retried (bounded by `maxAttempts`); invalid input is a permanent `failed`. Children exit if their supervisor dies, so a SIGKILLed worker does not leave solves burning CPU. Python never opens SQLite.
- **Pipeline:** one sequential job per run (spec §9 allows this in M1). Stages and artifacts: preflight, allocation, aggregation, clustering, travel, problem, solve, validation, summary. Manifests chain parent output hashes; input hashes cover parents, the stage's effective settings and producer version. No reuse yet.
- **Canonical JSON across languages:** Python's `canonical()` formats numbers exactly like `JSON.stringify` (ECMAScript Number::toString), so artifact hashes computed in Python verify in Node.
- **Semantics chosen:** preflight excludes lines at unresolved locations and pieces longer than a trailer before allocation (they never consume stock). Allocation is "order date, then net value per piece, then line ID". Visits are per-location whole-piece bundles filled in allocation order; split visits share one matrix node (PyVRP 0.14 clients can share a location). Auto-k takes the first k in 1…min(25, distinct locations) whose raw clusters pass diameter and `MAX_STOPS`; otherwise it repairs the last candidate by deterministic 2-means bisection (stable-ID split for duplicate coordinates; a single location with too many visits is chunked). Reachability is BFS from the depot over allowed legs, per cluster and globally, giving `unreachable_in_partition` vs `unreachable`. The objective is F = n·L + 1 per cluster (`truck_count_first_penalty`), range-checked against `MAX_VALUE / 4`; `weighted_distance` needs an explicit penalty. Validation recomputes loads from piece lineage and legs from the travel artifact; any failed cluster makes the plan `invalid`, partial coverage from unreachable visits keeps it `valid` with `coverage: partial`. `reconcile()` asserts the spec §10 identities per product and per unplanned reason.
- **Public API (spec §12):** `GET/POST /api/v1/runs`, `GET /api/v1/runs/:id`, `POST /api/v1/runs/:id/cancel`, `GET /api/v1/runs/:id/export?format=json|csv&table=loads|unplanned|clusters|products`, `GET /api/health`. Errors are `{ error: { code, message, fields } }`. Runs use only the bundled synthetic scenario; only `k`, `kmeans_seed` and `solver_seed` are overridable. **In production, creating or cancelling runs requires `RUN_KEY`** (`x-run-key` or `?key=`), the same narrow pattern as `REVIEW_KEY`, until quotas and isolation exist (spec §14). Reads stay public (synthetic data).

- **Contracts:** `ScenarioDocument`, `RunSettings` and `RunSummary` are Pydantic models exported to `schema.json`/`generated.ts`; the web validates run settings with the generated schema and the worker validates again.
- **Capabilities:** cluster diameter, graph reachability, the truck-count-first objective and independent validation are now `implemented`, each with a fixture; adapter version `pyvrp-partition/1`.
- **Image:** one image for web + optimizer. Python 3.13 is uv's managed CPython at `/opt/python` with the locked venv at `/opt/venv` (uv 0.8.2); runtime is `node:24-bookworm-slim` + tini, non-root, `HEALTHCHECK` on `/api/health` (database, queue, worker contact). `deploy/entrypoint.sh` starts the web server, waits for health (migrations run before it listens), starts the optimizer, and exits when either process exits. ## 2026-10-01: M4 experiments core (Claude Code)
- **Explorer jobs are runs** with `runs.kind = "explorer"` and an `ExplorerSettings` snapshot (`kind: "explorer"`, `base` RunSettings). The worker dispatches on `kind`; the job stores one `explorer` artifact. It clusters exactly the pipeline's population (`allocated_locations`, shared exclusion and allocation-order helpers). Task cap = `MAX_SWEEP_RUNS` (default 25), counting k × seeds plus one task per H3 resolution, so the default (2 k × 10 seeds + 3 H3) is 23. Never truncated.
- **Clustering method** is a run setting (`cluster_strategy`: kmeans | h3 | none, `h3_resolution` default 2). H3 groups by cell then uses the same bounded repair with `kmeans_seed` as the repair seed. `none` is the no-clustering baseline and fails permanently with `baseline_ineligible` when visits exceed `max_stops` or an enabled diameter limit; bounds still compare.
- **Inventory sweeps** use `inventory_percent` (stock × % rounded down) instead of new scenario versions; it is part of the preflight stage identity and of the comparison signature, so it forms a changed-assumption cohort.
- **Comparison signature** (`packages/db/src/experiments.ts`): scenario version, inventory %, eligibility (preflight policy, exclusions), capacity/units, metric definitions (version, travel and cluster circuity), validation rules (leg limit, diameter policy, pipeline version). k, seeds and method vary within a cohort. Default cohort = largest eligible; selectable and saved.
- **Ranking**: default order non-dominated → planned revenue ↓ → shipments ↑ → loaded miles ↑; Pareto vector planned revenue ↑, fleet utilization ↑, location-weighted mean centroid distance ↓; rounding cents / 1e-4 / 1 m; competition ranking (1, 1, 3). Invalid, partial, empty, unfinished, reused-solve and other-cohort runs are listed with a reason, never ranked. Rejected: a weighted score.

## 2026-10-01: M5 allocation strategies and whole-order mode (Claude Code)
- **One module, one depot.** `services/optimizer/src/fillrate_optimizer/allocation.py` holds every spec §8 strategy behind `allocate(lines, stock, strategy, policy, …)`. The scenario model has one depot, so there is no depot dimension or depot-selection variable yet; multi-depot sourcing waits for a model that has depots.
- **Settings:** `allocation_strategy` (`order_date_then_value` default, `first_come`, `priority`, `proportional`, `optimized`), `fulfillment_policy` (`piece` default, `whole_order`), `allocation_objective` (`revenue` default, `priority_then_revenue`), `respect_order_date` (false), `allocation_time_limit_s` (10, per stage). They are the allocation stage's effective settings; `fulfillment_policy` is also a preflight key because it changes eligibility.
- **Whole-order exclusion:** an order with any excluded line has its other lines excluded with the new reason `excluded_with_order` (stage preflight, counted as excluded in reconciliation), never filled from its eligible subset.
- **Proportional:** customer = `customer_id`, else the order ID. Piece mode follows the spec literally (floor of r × ordered per line, then single pieces to the customer with the lowest allocated ÷ target for that product, ties by the customer's next open line in date/value/ID order). Whole-order mode uses one fraction per customer across products (allocated pieces ÷ summed target pieces); an order that stops fitting is dropped for good because stock only falls. Labeled a heuristic.
- **CP-SAT:** one worker, seed 0, so equal inputs reproduce. "Weighted priority" = Σ priority × allocated pieces (pieces, not cents, so dollars are not mixed in); the revenue stage then constrains it to at least the best found and records a note if it was not proven optimal. "Respect order date" uses one monotone boolean per product and date ("some line on or before this date is short"), linear in lines rather than pairwise. The default greedy result is the hint when it is feasible (piece mode without the date rule). Shortage evidence for CP-SAT names the status and does not invent a priority trace.
- **Aggregation order** stays order date, then value for every strategy, so oversize-stop splits are the same regardless of how pieces were chosen.
- **Explorer population** (`allocated_locations`) now runs the same allocation as the run, so the k explorer clusters the locations the chosen strategy would ship.
- `Order.priority` (1–100, default 1) and an optional `priority` CSV column; regenerating `examples/` adds `priority: 1` to every bundled order (results unchanged).

## 2026-10-01: Hosted accounts, owner isolation and admission control (Claude Code)
**Decision:** Implement spec v1.10 §14 as three explicit modes, owner IDs on stored rows, and admission checked inside the store's queuing transaction.
- `FILLRATE_MODE=hosted|local`, with unset meaning the existing operator deployment, so the live site and image smoke keep working. Hosted mode refuses incomplete settings with exit 78. - Owners are strings: `operator`, `user:<Better Auth id>`, `examples` (public synthetic scenarios) and `public` (anonymous synthetic submissions). Existing imported data stays `operator`; nobody claims it by signing up. In hosted mode the operator key reaches only `operator` data.
- Reads follow the scenario's owner; cancel and ranking edits follow the submitter. Another owner's IDs answer 404, the same as missing ones.
- Stage reuse and geocoder answers are cached per owner. Travel snapshots stay content-addressed with one owner link per uploader, so a hash is never an access token.
- "One active job per account" counts submissions: a sweep or a geocoding job counts once. Daily solve admissions charge each sweep run. Cancelling does not refund, and idempotent replays are free.
- Hosted defaults: global queue 10, sweeps of at most 10 runs. Per-address limits and Better Auth's IP tracking use only an operator-named proxy header (`TRUSTED_CLIENT_IP_HEADER`).

Prizes are in the instance's cost unit but never part of a cost: the objective keeps its nominal `total` and adds `uncollected_prizes`, `prizes_collected` (information only) and `objective_with_prizes` (nominal + uncollected, what PyVRP 0.14 minimizes). The validator requires only required clients and cross-checks PyVRP's own prize totals. Schema version and fingerprints of instances without optional clients are unchanged; optional clients add their fields and a prize clause to the hashed objective definition.
- **Reason:** Folding a prize into costs would misreport spend and break comparisons with earlier runs; showing both terms and their sum lets a reader see why a stop was skipped.

## 2026-10-05: Saved manual baselines are strictly owner-scoped and only valid ones can warm-start (Claude Code)
- **Decision:** A saved manual baseline stores the plan with the evaluator's outcome and belongs to its saver, even on a bundled example's run; reads, deletes and warm starts compare owners only and another owner's id is 404. ## 2026-10-05: Fleet counts are fleet-wide; clusters solve in order against the vehicles left (Claude Code)
- **Decision:** An optional `fleet` run setting lists vehicle types (`id`, `label`, `count` or null for unlimited, `capacity` in hundredths of a foot, `fixed_cost_cents`, `per_mile_cents`). Every cluster's PyVRP model gets one native `VehicleType` per type (capacity, fixed cost, unit distance cost). A `count` is a **fleet-wide** limit for the dispatch, which PyVRP cannot express across independent clusters. Fillrate therefore (a) solves clusters in order, each against the count less what earlier clusters used (the model's `num_available`; a type with none left is omitted, and a cluster with no vehicles left has no candidate), and (b) sums every type across clusters in an independent check (`check_fleet`, recorded in the validation artifact) that marks the whole plan invalid with a concrete violation if any count is exceeded. The first part is a Fillrate rule around the solver and the second is validation; neither is called native, and the run summary carries an info diagnostic saying so. Unlimited types behave as the single trailer does today (one vehicle per visit).
- **Reason:** Per-cluster counts equal to the fleet-wide count could over-use the fleet by the cluster count, so a post-solve check alone would mark many feasible-looking plans invalid. Allocating counts before solving needs each cluster's truck demand, which is only known after solving. Sequential allocation never over-uses a fleet and is deterministic given cluster order, but it is greedy: an early cluster can take vehicles a later one needs (later cluster becomes `no_candidate`, never an over-used fleet). That limit is recorded in the capability `fleet_wide_counts` and the Provenance tab. A joint, cross-cluster assignment of vehicles is not claimed. Rejected: counts enforced only after solving; silently capping each cluster at an equal share.
- **Decision:** Without a `fleet` key the run is today's single unlimited `trailer_capacity` trailer: settings dumps, stage identities and stage outputs are byte-identical (golden digests recorded from the pre-feature pipeline are pytest-asserted on four examples). With a fleet, `trailer_capacity` is unused and left out of stage identity (`fleet` replaces it); stops are split to, and indivisible pieces and oversize stops are checked against, the largest type; fill and utilization are measured against each truck's own capacity; capacity lower bounds use the largest type. Comparison signature: the fleet (type `id`, `count`, `capacity`, sorted; not labels or rates) is part of the problem and forms its own cohort, shown as the changed assumption "Vehicle fleet". Warm-start plans and manual plans carry a vehicle type per route; a fleet plan only warm-starts a fleet run (`fleet_changed`) and mismatching types or counts are caught by the validator (`invalid_on_new_problem`); a manual plan without exactly one type per truck is refused. The replay bundle records the fleet identity (content hash of the types) and trucks per type.
- **Decision:** Truck-count-first with types: every type carries the same fixed cost F = n·L + 1 and unit distance cost 1. A plan with k trucks costs F·k + d, d ≤ n·L < F for any plan (open routes: n legs of at most L each, whatever the types), so fewer trucks of any type always outranks more, then distance: exactly the single-type objective, so the bound of spec §8b is unchanged and still proven. The type choice among equal-count plans is left to capacity and distance. A one-type unlimited fleet gives the identical PyVRP model and results (pytest). Cost objective: each type's fixed cents and per-mile cents become integer PyVRP coefficients `fixed·201168` and `mile·125`, divided by their common gcd over **all** types (one scale for the mixed fleet); cents are `objective × gcd ÷ 201168`, converted once at the boundary and checked by the evaluator; with one type this is exactly the existing single-type conversion. The cost objective with a fleet requires both rates on every type (the global rates are then unused); `weighted_distance` applies the same penalty to every type.
- **Not included (deliberately):** per-type max route distance and shift duration (PyVRP supports them but penalizes rather than forbids; the pipeline's validator would need new rules and the time adapter interplay is unproven), other load dimensions, per-type depots or profiles. The Solver Lab keeps those.

## 2026-10-05: Road geometry is fetched per inspected truck, only under the recorded Valhalla context (Claude Code)
- **Decision:** Valhalla `/route` geometry is available only for a run whose travel snapshot is `provider: "valhalla"` and only while the deployment's Valhalla identity (version, dataset revision, graph/config hash, costing, costing options) equals the snapshot's; estimated and imported runs are refused (`409 geometry_unavailable`, with a reason). It is fetched on request for one truck (never a whole run), chunked at `VALHALLA_MAX_ROUTE_LOCATIONS` (default 20) with one shared location, never resequenced, with no synthetic return leg, and cached in its own table (`route_geometry`, migration 0010) keyed by run, truck, snapshot and deployment identity. Each leg is compared with the snapshot's matrix and the difference is recorded, not hidden; a leg Valhalla cannot route is reported, never drawn straight.
- **Decision:** GeoJSON stays schematic by default; `&geometry=road` adds `valhalla_road` legs for fetched trucks only, labeled with the provider context and the note that the solver used the matrix. The web server decides eligibility and the optimizer re-checks it (identity, hash, coordinates). Fetches are synchronous, bounded and charged like plan evaluation (own daily/hourly buckets); transient provider errors are not retried.
- **Reason:** Spec §4 and §7 require road geometry to come from the same provider/profile/data context as the matrix and never to suggest the solver used those roads; a context rule that fails closed keeps the display honest, and per-truck fetches keep Valhalla load and quota bounded. Valhalla's route can differ from its matrix (CostMatrix values depend on block composition), so differences are data, not errors.

## 2026-10-06: Solver Lab groups are exclusive alternatives with no member prizes (Claude Code)
- **Decision:** Instance-level `groups` hold member client ids and `required` (default true: exactly one member; false: at most one). Members must be optional clients without a prize and belong to one group. Results add `groups` (`served_by` per group); an unvisited member is not a skipped prize. Schema version and the fingerprints of instances without groups are unchanged; groups add their ids, flags and sorted members and a clause to the hashed objective definition.
- **Reason:** In pinned PyVRP 0.14 the prize of every unvisited member of a group counts as uncollected (checked: a required group's solver picked the dearer member because the cheaper one's unvisited sibling carried a 1,000 prize). Forbidding member prizes keeps the group semantics in the validator and the reported objective unambiguous: the group decides, prizes stay for single optional clients.

## 2026-10-06: Solver Lab pickup-delivery pairs use PyVRP shipments with their own stops (Claude Code)
- **Decision:** A pair is native PyVRP `add_shipment` (verified in the installed 0.14.0: both stops on one route, pickup first, the amount on board in between), with its own pickup and delivery stops rather than references to clients. The load profile counts client deliveries still to drop plus pair amounts picked up and not delivered, and capacity is checked after every stop; route `load` stays the client deliveries (PyVRP's `route.delivery()` excludes shipments) while `peak_load` and utilization report the highest load on board. Pairs and reloads are refused together because how a reload interacts with goods in transit is not modeled. Capability id `paired_shipments` is kept; all UI text says pickup-delivery pairs. Schema version and fingerprints of instances without pairs are unchanged.
- **Reason:** Native pairing keeps precedence and same-vehicle rules in the solver, and recomputing the full load profile in the validator catches mid-route overloads that a start-of-route check would miss.
